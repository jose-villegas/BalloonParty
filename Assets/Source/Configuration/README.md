# Configuration

All game data is split across focused ScriptableObjects. Most are registered as singletons in
`GameLifetimeScope` and injected wherever needed. A handful that the single persistent camera and its
always-on backdrop fields need — `GameDisplayConfiguration`, `DisturbanceFieldSettings`,
`BackgroundFieldSettings`, `SkyScatterSettings`, and the direction/GI-facing interfaces of
`SceneLightFieldSettings` (`ISceneLightSettings`/`ITimeOfDaySettings`/`IScreenSpaceLightSettings`) — are
instead owned by `AppLifetimeScope`, the persistent app root that parents both the Launcher and Game
scopes; see `Assets/Source/README.md`.

Source is organized into per-context subfolders: `Balloons/`, `Buffs/`, `Cinematics/`, `Effects/`, `GridActors/`, `Items/`, `Level/`, `Palette/`, `Ranges/`, and `Editor/` (drawers). The tables below note the subfolder where it isn't obvious.

| `LevelPacingConfiguration` | `ILevelPacingConfiguration` | How levels pace (`Configuration/Level/`). Every positive level's mix is **generated** by `LevelGenerator` from the `_generation` block (`LevelGenerationSettings`, see Data types); `ParametersForLevel(level)` returns it as a `RangedLevelParameters`, and `SeedForLevel(level)` is the level's seed. The `_ranges` array now holds only negative-keyed **debug presets** (`-100`…, reached by the start-level cheat with a negative level), exposed as `DebugPresets`. Also holds the `ThresholdModifier`/scoring curve (the points each level asks, fitted to how long a level should take: `Docs/level-balance.md`, refitted with `Tools/balance/level_balance.py`) and the `_spawnClock` block (`SpawnClockSettings` / `ISpawnClockSettings`, exposed as `ILevelPacingConfiguration.SpawnClock`) — *when* lines arrive, independent of the per-level *what*: first-level interval (1.7 s), per-level decay (×0.95) down to `MinInterval` (0.9 s), then a late decay (`LateIntervalDecayPerLevel`, ×0.98) down to `LateMinInterval` (0.55 s), so lines keep speeding up on deep levels where the generator has nothing left to add, start-of-level `GraceSeconds` (2.5 s), `LinesPerWave` (3), `OverlapShotPull` (0.35: the share of the current wait a ball fired while another is flying takes off the next line), `SparseBoardSpeedup` (8: how much faster the clock runs on an empty board), `TargetOccupancy` (0.5: the share of open slots the clock pushes balloons towards) and `OccupancyWeight` (0.5: how the board's fill is read, 0 = against the level's starting fill only, 1 = as occupancy against the target only). The clock eases to normal pace as that blended fill reaches 1. On top of that board pace, `FlightSpeedup` (3) and `FlightPressureSeconds` (6) add flight pressure: the summed flight time of every ball in the air, full at 6 s, adds up to 2 more times the pace. A big clear earns a breather: losing `BreatherClear` (0.15) of the open slots within `BreatherClearWindow` (2.5 s) drops the clock to `BreatherPace` (0.2 of its full pace), easing back to full over `BreatherSeconds` (11 s), and `BreatherCooldownSeconds` (14 s) of play must pass after it before the next; 0 clear turns it off. Score shapes covering `BreatherShapeCover` (0.5) of the play area start the same breather; 0 turns that off. So does danger at `BreatherDanger` (1) or more, a full board on the last heart (0.5 adds the second to last); 0 turns that off. Pressure (`PressureSpeedup` 2×, `PressureBuildSeconds` 120 s, `PressureHoldOccupancy` 0.85, `PressureKeptOnHeartLoss` 0.5) pushes back on a comfortable player: it builds while the board stays under the hold and the player is not in need, and runs the clock up to the speedup. `IntervalForLevel(level)` is the only read the spawn clock needs; levels below 1 run at level 1's pace. `Mushrooms` exposes the `_generation` block's mushroom settings (`IMushroomSettings`, see Data types), which `GameLifetimeScope` registers under that interface. Resolved into the live `LevelParameters` by `LevelDifficultyResolver` (`Game/Level/`); consumers read `IActiveLevelParameters.Current`, never this SO directly |

### Data types

| File | What it does |
|---|---|
| `BalloonPrefabEntry` | Serializable entry in `BalloonsConfiguration` — holds a `BalloonView` prefab reference, spawn weight, optional max-count cap, `HitsToPop` (how many hits before popping; -1 = unbreakable), `ScoreValue` (points awarded on pop), per-type `NudgeOverride[]`, per-outcome `HitVfxOverride[]`, and a `PopPulse`. `BalloonType` drives which model class is created (`Simple` → `BalloonModel`, `Tough` → `ToughBalloonModel`). Item eligibility is determined by whether the model implements `IHasWriteableItemSlot` — not a flag. Pool key is derived from the prefab's GameObject name. |
| `GridActorPrefabEntry` | Serializable entry in `GridActorConfiguration` — holds a `GridActorView` prefab reference, `GridActorType`, `SlotPlacementMode` (`Random` or `Cluster`), and `HitsToPop` (relevant only for `Gatekeeper`). Per-level spawn count and cluster cap come from the level pacing gate (`IActiveLevelParameters.TryGetGridActorGate` → `ResolvedGridActorGate`), not the entry. Pool key is derived from the prefab's GameObject name. |
| `MushroomSettings` / `IMushroomSettings` | Serializable tuning of the meadow's mushrooms (`GridActors/`, `Plans/PLAN-MeadowMushrooms.md`). `Rules` (`MushroomChainRules`, in `Shared/`): `ChainTarget` (3 hits in one flight arm the lance; nothing is paid past it, since the ball is a lance from there and cuts caps instead of bouncing off them), `RepeatHitCounts` (off: the wall of caps hit last counts again only after another) and `MaxBouncesPerStretch` (12: the most bounces off mushrooms between two walls, after which they let the ball through; a chain is paid by its third counted hit, and 0 or less reads as 12, never as no cap). The bounce: `ForgivingKick` (on) and `Kick` (`BumperKickTuning`, in `Shared/`): `ConeDegrees` (20: how far from the mirror reflection a cap of another wall may lie and still pull the bounce toward it; it is the dial for how much skill a rally asks, narrowed from 30 by the owner), `MinOffset` and `MaxOffset` (0.15 and 0.9: how near a cap's centre, and how near a graze, a kicked ball may land, as a share of the radius it bounces at; they are also the turns a kicked ball can make, 163 down to 52 degrees). `Radius` (0.3 world units, without the ball's). `Placement` (`MushroomPlacementLimits`, in `Slots/Actor/`): 2 to 4 walls of caps (a wall is 1 to 3 caps in neighbouring slots), 4 to 7 caps in all, `MinSpacing` (1.9 world units, two and a half slots: the least two walls stand apart, nearest cap to nearest cap, like the bumpers of a pinball table; never read as less than the room a ball needs between two, and 0 or less reads as 1.9), the columns and rows kept clear, and `Band` (`MushroomLayoutBand`: what a layout must measure, flown from every aim angle on an empty board, to be in the baked catalogue the levels are dealt from: 7 to 16 in 100 angles arm the lance, the widest unbroken run of them spans 2 degrees or more, and at least 20 angles arm) and `Cannon` (`MushroomCannonClearance`: the room a layout must leave the cannon to be in the catalogue: `MinDistance` (3.25: no cap's centre nearer the point the cannon turns about at rest, which keeps the lowest row a cap may stand in empty), and `MaxShadowShare` of the aim angles (0.2) at the most whose first straight leg from the muzzle meets a cap within `NearRange` (4), so no wall stands side-on across the cannon's view). The layouts themselves are baked to these numbers (`Slots/README.md`, *Mushroom placement*): after changing the cone, the offsets, the radius, the rules or the placement, bake the catalogue again (`Tools > BalloonParty > Bake Mushroom Wall Catalogue`), or `MushroomAimGridTests` fails. `PermanentSlotLimit` (9): the slots the mushrooms' caps and the bushes may take together. `Lean` (`MushroomLeanTuning`, in `Slots/Actor/`), how a cap answers a hit: `LeanPerSpeed` (0.014 world units of lean at its furthest for each unit of the ball's speed, so 0.14 for a shot off the cannon, nearly the most: seen from above, the stem under the cap shows only once the cap has been knocked well off its foot), `MaxLean` (0.15, the furthest it ever leans), `Frequency` (3.6 wobbles a second) and `Damping` (0.16: low, so the cap swings back past its rest a few times), `RewardPulse` (1: how far the cap swells when a bounce pays the lance, as a share of the material's full swell and glow) and `RestLean` (0.0015: under it a cap that has also stopped is still, and its view switches off), and `SwayLean` (0.15, never more than `MaxLean`: how far a bomb's blast leans a cap it sways at full strength, before the cap swings back). `RegrowBeats` (5: how many of the board's beats a cap a lance cut stays gone; it grows back on the beat that brings its count to this, so between 6.8 and 8.5 seconds with the beat at 1.7; never read as less than 1). `Blast` (`MushroomBlastTuning`, in `Shared/`), what a bomb does to the mushrooms it does not take the caps off: `SwayShare` (2.4: how far the bomb sways them, as a share of its kill radius; at 1 a mushroom sways when its cap overlaps the kill radius, which on the shipped board is the ring of slots past the ones next to the bomb, faintly and under the bomb's own cloud, so it ships wider: at 2.4 the reach is 3.3 and the third ring, outside the cloud, sways at about a half; 0 turns it off, and it is never read as under 0). Which caps a bomb takes off is no setting: it is the bomb's own rule for what it breaks outright (`Item/Bomb/BombBlast.Pierces`). `Cut` (`MushroomCutTuning`, in `Slots/Actor/`), how a cap a lance has cut falls and pops back, the look only (when a cap is cut is the rule's to say, and when it grows back is `RegrowBeats`): `FallSeconds` (0.6, from the cut until the two pieces have faded out), `PartDistance` (0.16 world units each piece ends up from the cut line, to its own side) and `CarryDistance` (0.08 along the lance's way), `TurnRadians` (authored in degrees: 14, one piece each way), `EndSize` (0.55: a piece's size when it reaches the ground, as a share of its size on the stem; it shrinks toward its far rim, and at this size its cut edge has drawn back off the stem by the end), `RegrowSeconds` (0.35) and `RegrowOvershoot` (0.1: how far past its size the cap swells as it pops back); `Spores` (`MushroomSporeTuning`, in `Slots/Actor/`), what a mushroom lets go (`Slots/README.md`): `Refractory` (0.4 seconds a mushroom keeps quiet after a hit's puff), `Budget` and `BudgetPerSecond` (18 and 3: what the whole board may let go at once, counted in hits, and how fast it comes back), a hit's puff (`MinSpeed` 2 and `FullSpeed` 9.8, the ball's speeds for nothing and for all of it; `Length` 1 and `EndWidth` 0.6, the smoke's cone, longer than a cap is wide; `Smoke` 0.9, its share of the smoke profile's opacity (the field shows nothing of a stamp under about a third); `Specks` 10; `PaidScale` 1.5 for the hit that pays a chain), `CutScale` (2) and `BlastScale` (6), a cut's and a blast's as multiples of a full hit, `BlastDelay` (0.45 seconds, for the bomb's own cloud to thin) and `BlastFanDegrees` (170), and the specks (`SpeckSpeed` 3.4, `SpeckSeconds` 1.1, `SpeckSize` 0.09, which most are under and a few well over, `SpeckGreen` and `SpeckBlue`, the two colours each is between). The numbers were about half these until the owner asked for more (PLAN-MeadowMushrooms, *Bigger spores*). `Idle` (`MushroomIdleTuning`, in `Slots/Actor/`), what a cap does while nothing touches it, all of it the shader's work (PLAN-MeadowMushrooms, *An idle cap*): the breath (`Breath` 0.08, the swell at its top as a share of the radius, only ever outward of the circle the ball bounces off; `BreathSeconds` 2.6; `PhaseSpread` 0.1 and `WaveAcross` 0.2, how far apart two mushrooms' breaths are by their seeds and by a world unit across the board; `ShadowLift` 0.8, `GlowSwing` 0.4 and `WartSpread` 0.08, what rides it) and the rocking in the disturbance field (`RockPerDisplacement` 0.16 world units of lean for a unit of the field's displacement squared, `RockMost` 0.065, `RockSeconds` 0.45, `RockSwing` 0.6, the share of the lean that swings). The smoke's colour and how long it lingers are the smoke field's (`SmokeFieldSettings`, the `MushroomSpores` profile: about a second for a hit's puff, two and a half for a blast's cloud). `Blown` (`MushroomThrowTuning`), how a cap a blast blows off flies, whole: `Seconds` (1.1 in the air), `Distance` (0.9 world units thrown, away from the blast), `Lift` (0.25: how much larger it is drawn at the top of its throw; its shadow lies up to `ShadowLift` times as far off it, 2.25) and `TurnRadians` (authored in degrees: 40). `RoomBeyond(radius)` is the room what came off needs past the cap's own radius by the bound the shader boxes it with (the radius times the lift and the turn, plus how far it is moved; the larger of a cut's and a throw's), which the builder sizes the quad for. `Validate` adds a message for each number that cannot work with the others (a cap on bounces under what a chain takes, crossed offsets, a cone too narrow for two walls to send the ball back, a spacing under two caps across, fewest walls over most, fewest caps over most, most caps under the most walls, caps that leave the bushes fewer than 2 slots, a band with its ends crossed, a ceiling that lets no aim angle meet a cap within the cannon's near range, a count of walls the baked catalogue has no layout for, a furthest lean over half the radius, which would carry the cap off the quad it is drawn on); `LevelGenerationSettings.Validate` calls it, so they show with the Level Pacing asset's other issues. The kept-clear rows and the shared limit are first guesses, to be tuned in play; the spacing, the band and the cannon's room were measured, and the cone is the owner's (the plan's *Spacing as built*, *Walls with a kick as built* and *Walls with a kick, after its review*). ## Design rules

- **Never hardcode** values that exist in a configuration asset.
- **Never duplicate** configuration data via `[SerializeField]` on individual systems. If a system needs a value, it injects the relevant configuration object.
- **Always inject the read-only interface**, not the concrete SO type. Every configuration SO has a corresponding `I`-prefixed interface (`IBalloonsConfiguration`, `IGamePalette`, etc.) that exposes only read-only properties. `GameLifetimeScope` registers each SO via `RegisterInstance<IInterface>(so)`. This prevents accidental mutation of SO fields at runtime and decouples consumers from the SO class.
- New configuration fields are added to the appropriate asset type. When a domain of settings grows large enough to stand alone, extract it into its own ScriptableObject rather than bloating an existing one.
- Cross-assembly configuration interfaces live in `Shared/` (not `Configuration/`) because they are consumed by assemblies that do not reference the `Configuration` namespace. Examples: `IProjectileFlightConfig`, `ISlotGridConfig`, `IPredictionTraceConfig`, `IRunConfig`, `IScoreTrailConfig`. All other configuration interfaces live alongside their SO in `Configuration/`. These five focused contracts replaced the former single `GameConfiguration` / `IGameConfiguration` umbrella, which was decomposed into `ProjectileFlightConfig`, `SlotGridConfig`, `PredictionTraceConfig`, `RunConfig`, and `ScoreTrailBehaviourConfiguration` (score-trail timing) plus `ProjectileVisualConfig` (projectile-death presentation) and removed entirely.
- New common fields added to `ItemSettings` or `BalloonPrefabEntry` appear in the Inspector automatically — no drawer changes required. Only fields that need custom layout (variable height, conditional visibility, custom controls) must be added to the drawer's `ExcludedFields` set.
- Collection properties on interfaces use `IReadOnlyList<T>` to prevent element assignment and mutation of the collection structure. The backing `T[]` or `List<T>` in the SO satisfies this implicitly.
- **Editor config lookups** must use `ConfigAssetCache<T>` (in `Shared/`) instead of inline `AssetDatabase.FindAssets` + `LoadAssetAtPath`. This caches the result after the first lookup and avoids repeated asset-database queries. The class is guarded by `#if UNITY_EDITOR` so it compiles away in builds, but is available to both runtime `OnValidate` blocks and editor code. The `config-asset-cache` audit rule enforces this in editor files and `#if UNITY_EDITOR` blocks everywhere.
