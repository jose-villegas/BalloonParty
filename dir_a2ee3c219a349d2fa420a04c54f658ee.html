Detailed Description

Items are game-wide collectible effects — Bomb, Laser, Lightning, Paint, Shield, and Snipe. They can appear in different contexts throughout the game: on balloons, in UI previews, in reward screens, or anywhere else an item needs to be displayed or activated. The item system is intentionally context-independent — it knows how to display and activate items, but does not know or care what is hosting them.

ItemAssigner IStartable — subscribes to ItemCheckMessage. On the initial board fill (IsInitialSpawn) it rolls InitialItemCountWeights; on a cadence turn (TurnCount % ItemCadence == 0) it rolls ItemCountWeights. Each is an AnimationCurve weighted distribution (X = item count 0,1,2…, Y = weight) sampled fresh per turn via SampleCount, so the count is a random draw, not a per-level constant. It then grants that many items across distinct newly-spawned IHasWriteableItemSlot balloons (capped by how many are eligible), re-picking a weighted type per grant and tracking the running per-type count so MaximumAllowed holds within the batch. Balloons without IHasWriteableItemSlot (e.g. ToughBalloonModel) or already holding an item are excluded. Cap counting pattern-matches grid actors on the same IHasItemSlot capability eligibility uses — counting a concrete model type would silently break the cap. Shields skip the weighted draw while IRunConfig.PlanShieldChains is on: see Shield chains below

Range preview (Preview/)

The aim-time telegraph (Item Range Preview): while the prediction line of sight crosses a balloon hosting an item, that item's affected area is drawn on the board by ribbon "pens" streaming out of the host. Borrows the technique from the score-trail formations (Game/Score/Behaviours/) — heads dragging TrailRenderer ribbons trace a figure — but these are flat, board-space, and anchored to a balloon rather than 3D polyhedra flying at a UI bar.

File What it does
IItemRangePreview The seam — ItemType Type plus BuildShape(in context, shape). One implementation per item type, resolved by Type exactly as ItemActivator resolves IBalloonItem, so a new item ships its preview beside its handler with no dispatch table to edit. BuildShape is pure geometry: it appends points and never touches a renderer, the pool, or Time — which is what keeps every figure edit-mode testable and lets one driver animate all of them. An implementation with an existing config-free core for its shape (PaintTriangle, LightningChain, BombBlast, LaserCross) must build on it rather than re-derive, or the telegraph drifts from the effect it advertises
ItemPreviewShape / ItemPreviewStroke The shared vocabulary: a figure is a set of strokes (polylines), each a range into one flat point list. A circle is one closed stroke, a plus two open ones, lightning one per arc. Reused across rebuilds (cleared, never reallocated). AddCircle/AddSegment cover the common cases; a stroke of fewer than two points is discarded rather than recorded, since it has no arc length for a pen to travel
ItemPreviewEntry Pure polyline-vs-polyline math — where the aim's own trace first crosses one stroke, as an arc-length offset along that stroke — factored out so it is edit-mode testable without the ticker's pen/pool machinery, mirroring TraceHitGeometry. TryFindEntryOffset walks the trace segment by segment (not the stroke segment by segment) so "first" means earliest along the shot's own direction of travel, including a closed stroke's wrap leg as a segment; ties within one trace segment are broken by the intersection nearest that segment's own start. Alongside the stroke-side offset it also reports the crossing's own trace-side arc offset — the distance from the trace's first point to the crossing, measured along the (possibly bent) trace itself — which is what lets the stroke's approach cascade follow the trace instead of cutting a straight line to it (see ItemPreviewTicker below). Returns false (both offsets 0) when the trace never crosses the stroke at all — ItemPreviewTicker treats that as "start this stroke's draw-in at its own beginning, and fall back to a straight-line approach" rather than a failure. TryFindNearestPointOnPolyline is the other shared projection: the closest point on an arbitrary polyline to a target, plus that point's own arc-length offset from the polyline's first point. ItemPreviewTicker calls it once per Show/refit to place the host on the retained trace copy (_hostTraceOffset, anchoring the approach cascade); SnipeRangePreview calls it directly to anchor its pierce corridor on the same trace instead of the host centre. False when the polyline has fewer than two points, the same degenerate case its caller falls back from

ItemPreviewViewport Plain C#, DI singleton — the one shared owner of "what is visible": the camera-derived world rect, expanded by a margin derived from IItemPreviewConfig.DashLength. ItemRangePreviewController IStartable/ILateTickable, plain C# — decides which item hosts the aim is sighted on and drives the visible figure through them in sequence: every host the line of sight crosses, ordered first-to-last along the line, draws in one after another and wraps back to the first once the last finishes — see "The figure loops, and now it advances" below. Plain C# rather than a component on the balloon, because it needs DI singletons a pooled item visual would have to be hand-threaded, and because only one preview shows at a time — a global arbitration a per-balloon component cannot make. CollectSightedHosts walks the grid collecting every candidate TraceHitGeometry scores a hit on and that has a registered preview (into the reusable _sightedHosts, no per-frame allocation), then ItemPreviewSightOrder.OrderAlongTrace sorts them by each host's own projection onto the trace (ItemPreviewEntry.TryFindNearestPointOnPolyline) — a deliberately different question from Centrality (how squarely the line crosses a balloon), which the grid walk still computes (TraceHitGeometry always reports it) but no longer uses to pick a winner, since a sequence has no single winner to pick. The figure only ever draws while the aim is settled: any change to its inputs hides it and restarts IItemPreviewConfig.SightDelaySeconds from zero, so SightDelaySeconds gates every appearance now, not just the first. "Changed" is a two-part signature now — the set (_signatureSlots, the sighted hosts' slots in trace order) and the active host's own continuous geometry (origin, aim direction, and PredictionTraceProvider.End's contact kind/normal, which Shield's stub depends on) — each compared against the last frame they held, past a small jitter epsilon for the geometry half and exact per-slot equality for the set half. Splitting it this way is what lets the sequence advance without looking like the aim moved: stepping from host 2 to host 3 changes the active host's origin/direction (a different balloon) but not _signatureSlots (the same set of balloons is still sighted), and only the set half gates a full hide-and-restart. Not PredictionTraceProvider.Version: SetTrace bumps it unconditionally and ThrowerController.UpdatePredictionTrace calls it every Tick while aiming, so it changes every frame regardless of whether the aim moved and cannot serve as a movement signal (the grid walk below is still nominally gated on it, but that gate never actually skips anything while aiming — a separate, known cost this change doesn't attempt to fix). Once a signature has held for the delay, Show is called exactly once for the sequence's first host and not again while the set keeps holding — re-calling Show outside of a cycle boundary (or a settled spin re-bloom, see below) is what would reposition a shown figure's pens, so not calling it otherwise is what buys the invariant this whole scheme exists for: a figure's pens never reposition while it is visible, which is what eliminates the ribbon-streaking repositioning used to cause, by construction rather than by patching it after the fact. A changed signature calls ItemPreviewTicker.BeginHide() (the graceful fade, see below) rather than Hide(), so the old figure fades rather than cutting; the next Show — once the new signature settles, always at sequence index 0 — naturally draws itself in again from its strokes' entry points, since BeginHide already dropped _visible. SightDelaySeconds == 0 still shows on the same frame a signature first stabilizes, not one frame later. Refreshes ItemPreviewViewport at the top of LateTick, before building the context that carries it. Tracks the SET last actually shown (_shownSetSlots), separately from the signature machinery above, and passes introduce: true to ItemPreviewTicker.Show only when that set differs from the one being shown now (a genuinely new set, or the first one) — a re-settle on the SAME set after an aim nudge passes false, so the draw-in plays once per settled set rather than on every re-settle. Compared as a whole set, not a single slot, precisely so that stepping through an unchanged set never reads as a detour off it. Cleared whenever the telegraph goes away entirely, so looking away and back at the same items introduces again. Also cleared the moment RefreshSightedHosts finds a sighted set that isn't _shownSetSlots, even if that newly-sighted set never itself dwells long enough to be shown — _shownSetSlots is a "last actually shown" cache, only written once a signature has dwelt its way to a Show, so without this a quick detour through a different set (or back off this one) between two dwells on the same original set would otherwise leave _shownSetSlots pinned on it the whole time; by the time the aim resettles there, the sighted set matches _shownSetSlots again and the detour is invisible to the introduce check, so the figure would reappear already formed instead of re-blooming. Also the one to advance a looping figure: it polls ItemPreviewTicker.CycleComplete each LateTick and, on an already-shown signature, responds via AdvanceSequence — see "The figure loops, and now it advances" below for why deciding what draws next belongs here rather than in the ticker. A spinning host's angle is deliberately not part of the signature above — see "A spinning host re-blooms instead of resetting" below for why, and for the separate accumulator that keeps a fast-rotating host from starving the sequence it's part of
ItemPreviewSightedHost / ItemPreviewSightOrder The sequencing seam, alongside ItemPreviewEntry. ItemPreviewSightedHost is one sighted host — slot, resolved IItemRangePreview, origin, aim direction, plus a TraceOffset filled in after the fact. ItemPreviewSightOrder.OrderAlongTrace is pure geometry: given a set of sighted hosts and the trace polyline they were found on, it projects each host's origin onto the trace (ItemPreviewEntry.TryFindNearestPointOnPolyline) and sorts by the resulting arc offset via a cached IComparer<T> singleton (never a per-call Comparison<T> delegate, since the grid walk that feeds it runs effectively every frame while aiming) — factored out of the controller specifically so the interesting case, a bent multi-segment trace where a host spatially near the aim's own origin can still sequence last, is edit-mode testable without the controller's grid/pool machinery
ItemPreviewTicker ILateTickable — drives the pens closed-form off one clock, no tweens or coroutines, mirroring ShapeFormationTicker's zero-allocation constraints. The draw-in is a cascade: every pen is confined to its own dash, and dashes reveal one at a time, in a relay, rather than every pen tracing the same shared path at once (see "Why a cascade" below). Once per Show, after the arc table is built, ItemPreviewEntry.TryFindEntryOffset finds where the aim's own line of sight first crosses each stroke and records it as the stroke's entry offset (falling back to 0, the stroke's own start, when the trace never crosses it at all — true of Lightning's later arcs, which the trace only reaches through the chain), and BuildEntryOffsets also resolves it to a world point (_entryPoints) and, alongside the trace-side offset the helper reports (_entryTraceOffsets / _entryTraceValid), the arc-length distance the stroke's own approach cascade actually covers (_approachLengths) — along the trace, between the host's own position on it (_hostTraceOffset, resolved once per Show/refit by BuildTraceBuffers as the nearest point on the retained trace copy to _origin) and the stroke's own entry trace offset, when the helper found a crossing; the straight-line distance to _entryPoints otherwise, exactly as before this existed. The entry offset no longer defines a travel destination for every figure pen — it only does two things now: it ranks the cascade order (ComputeTravelDistance returns each dash's forward arc distance from the entry — Mathf.Repeat(slotOffset − entryOffset, strokeLength) on a closed stroke so the ranking always reads as one forward sweep round the shape, or the plain signed difference on an open one, which still ranks correctly since a slot's raw position and its distance from the fixed entry differ only by a constant offset; AssignCascadeRanks turns that ordering into each pen's CascadeRank, smallest first, once per Show/refit, never per frame), and it anchors the stroke's approach cascade, described below. BuildCascadeTimings splits BloomDuration into each stroke's own windows once per Show/refit: the approach gets a share proportional to its length against the stroke's total path (approachLength plus every dash's own painted length), and the remainder divides evenly across the stroke's dash count, so figure pen k's window starts exactly when pen k − 1's ends (_approachDurations / _dashDurations, one pair per stroke). Every stroke reads the identical shared clock — elapsed = BloomCurve.Evaluate(Clamp01(BloomElapsed / BloomDuration)) * BloomDuration — against only its own window bounds, which is what makes several strokes (Laser's two lines, Lightning's arcs) cascade in parallel: each stroke's relay runs on its own schedule over the same tick, so a two-stroke figure draws both at once rather than taking twice as long. AdvanceCascade is now uniform across every figure pen, CascadeRank == 0 included: each one simply waits Parked and pen-up at its own dash's start until its window [windowStart, windowStart + dashDuration) opens — rank 0's window starts at exactly approachDuration, i.e. the moment the approach cascade's own last dash finishes — then sweeps, via the shared clock, from its dash's own start (DashIndex * slotLength) out to its dash's own end (+ painted, the same painted length AdvanceDash uses); this is drawing, not travelling, the pen never leaves its own slot. The moment a pen's window closes (localT >= 1) it becomes Bloomed — pinning Distance to painted, the ping-pong's own peak — and hands off to the existing per-slot dash sweep (AdvanceDash) unchanged; the two formulas agree exactly at the handoff, so there is no positional jump at the seam, and AdvancePen stops calling AdvanceCascade for that pen from then on. Show distinguishes a new host (every pen restarts its cascade from BloomElapsed = 0) from the same host re-fitted (pens keep their bloom progress; only CascadeRank and the stroke's windows are recomputed against the reassigned slot) — though with the controller now only calling Show once per settled signature (see above), the re-fit path is a dormant fallback rather than one it exercises in normal play. A re-fit also re-derives the per-stroke dash counts, entry offsets and cascade timings, not just the arc table, because a figure can reshape while its host stays put — Laser's hex-stepped rotation is the case that forces this, since its beams' clipped length swings every step even though the host doesn't move. Hide() releases every pen (figure and approach) to the pool immediately, for teardown; BeginHide() is the graceful counterpart the controller calls instead — it stops every pen emitting (HighlightTrail.SetEmitting(false)) but leaves them in place, so whatever ribbon they'd already laid fades out on the TrailRenderer's own lifetime rather than the figure cutting out. LateTick stops advancing pen positions entirely while fading, so a fading figure hangs where it stopped instead of continuing to sweep. Once the fade has run for the pens' own ribbon lifetime (read off a live pen via HighlightTrail.EffectiveRibbonSeconds — the pen prefab's own authored TrailRenderer.time, shared by every item now, rather than a duration re-authored on the ticker), the pens are released exactly as Hide() would. A Show arriving mid-fade cancels it outright rather than letting it run to completion underneath the new figure: it clears the fade flag and, because BeginHide already dropped _visible, always takes the acquire path — reusing the still-held pens (no pool round-trip) and cascading them in again, which is the intended fade-in and needs no extra machinery. The draw-in is an introduction, not a per-Show effect: Show's introduce parameter (decided by ItemRangePreviewController, see above) tells AcquirePens/AcquireApproachPens whether the pens they hand out should start life mid-cascade or already settled — for a figure pen, Bloomed = true and BloomElapsed past the bloom duration, so AdvancePen takes the settled branch on the pen's very first tick and it simply appears in place, the same settled state a pen gets when RefitPens grows the figure a new slot. Every figure cascades this way now — there is no longer a per-item opt-out, since the per-item style layer had nothing left to say once the draw-in became universal.

The approach is its own dashed cascade, drawn by pens that retire rather than settle. The leg from the host origin to a stroke's entry point used to be one pen (CascadeRank == 0) sweeping it as a single continuous, emitting stroke. It now reads as a comet: the same leg, on the same DashLength/DashSpacing stride the figure's own dashes use, split into dashes by DeriveApproachDashCounts (mirroring DeriveDashCounts, via the same ComputePaintedLength gap-pinning), one dedicated ApproachPen per dash, cascading host-to-entry inside the existing approachDuration window BuildCascadeTimings already reserved for that leg — splitting that window evenly across however many approach dashes there are, so the figure's own first dash still begins exactly when the leg's own window would have closed either way. Why not just toggle one pen's emitting, the way a dash-count-1 stroke would suggest: TrailRenderer keeps its recorded points when emitting goes false and appends to them when it goes true again, so each gap in an on/off leg would be bridged by a straight chord the instant the pen re-lit — exactly the discontinuous-emit failure the standing rule below exists to prevent. Clearing the ribbon at each re-enable avoids the chord, but it also erases the dash the pen had just drawn, so a single pen literally cannot leave a dashed tail behind itself — there is no toggling pattern that produces one. Hence one pen per approach dash. AdvanceApproachPen is that pen's whole lifecycle, and it is deliberately simpler than a figure pen's: before its window opens it sits Parked-equivalent — pen-up, at its own dash's start, same discontinuous-jump rule as everywhere else in the file — then sweeps its dash once, and the instant that sweep finishes it retires unconditionally: RetireApproachPen positions it at the dash's own end and flips Retired true (and Emitting false) — it never emits or moves again until the next Show re-acquires it. There is no tail-extension phase; a pen that has drawn its dash is simply done. Retiring is not a simplification for its own sake — it is the mechanism that produces the comet's fade: a stationary ribbon ages out purely on the TrailRenderer's own m_Time, unmanaged, so the dash drawn earliest (nearest the item) has been aging the longest by the time dashes further out are still being drawn, and the tail thins visibly behind the advancing front with no per-pen alpha or colour control anywhere — the tint path was deliberately deleted from HighlightTrail once already (see its row below) and retiring is what lets this effect stand without bringing it back. A retired pen stays allocated, not returned to the pool, until the next Show — pooling it early would despawn its ribbon (and the tail it's carrying) instantly, cutting the comet off mid-fade; ReleasePens is what actually returns it, on Hide() or a fade's natural completion, exactly like a figure pen. ResizeApproachPens/AcquireApproachPens/RefitApproachPens mirror the figure's own ResizePens/AcquirePens/RefitPens one level down: introduce == false (a re-settle on an already-telegraphed host) has no cascade to relay through, so SettleApproachPen paints the dash directly — start position, emit on, end position, emit off, then retired — instead of cascading in, exactly mirroring how a re-settled figure dash reappears already mid-ping-pong rather than blooming in again. Approach dashes draw from the same MaxPens budget as the figure's own — DeriveApproachDashCounts derives them on the same stride, but against what's left of MaxPens after the figure's own dash count is subtracted, and forces every stroke to zero approach dashes outright once that remainder hits zero, rather than ever letting a long approach crowd out the figure it leads into (see "A pen cap bounds the total" above). A near-zero approach — Laser, Paint, and Snipe's whole line, Lightning's first arc, anywhere the entry already sits on the host — derives zero approach dashes by construction, not one degenerate dash rounded up from a tiny length; so does any approach merely too short, not just zero: ApproachDashCountForLength returns 0 whenever the leg can't fit a full DashLength + DashSpacing stride (measured against whatever stride the caller passes in, authored or budget-inflated), rather than flooring at one dash whose ComputePaintedLength would immediately collapse toward the slot * 0.1f fallback and read as a point rather than a dash — Bomb and Shield's own approaches clear the threshold comfortably and keep their RoundToInt counts unchanged. Zero approach dashes on a stroke is a fully supported state, not merely a tolerated one: BuildCascadeTimings gates a stroke's approachDuration on its actual _approachDashesPerStroke count (not just a nonzero approachLength), so a stroke with no approach pens — whether from a near-zero entry, a too-short leg, or the shared MaxPens budget starving it — reserves no approach window at all and its figure dashes cascade across the whole BloomDuration starting at t = 0, rather than the figure waiting out a window nothing was ever going to fill. This is why AcquirePens/RefitPens now call DeriveApproachDashCounts before BuildCascadeTimings: the timings need the approach dash counts already resolved. Ribbon lifetime is the knob that decides how much of a figure you can see at once. A pen paints TraceSpeed × ribbon seconds of world length before its tail fades. The figure loops: draw in, hold, fade out, then draw in again — but replaying is ItemRangePreviewController's call, not ItemPreviewTicker's own, and now that call is "the next host in line," not just "the same one again." Once a figure's draw-in finishes, the ticker doesn't leave it settled forever — it walks an explicit three-phase state machine (CyclePhase: Drawing → Holding → Fading) off a single ticker-level clock (_cycleElapsed, advanced in LateTick via AdvanceRebloomCycle) rather than polling every pen for "am I settled yet," since every pen already ticks against one shared BloomElapsed-derived clock by construction. Drawing lasts BloomDuration, Holding lasts IItemPreviewConfig.RebloomHoldSeconds; once Holding elapses, BeginLoopFade stops every pen emitting and lets their ribbons age out on their own lifetime — the figure visibly fades before the next draw-in, rather than vanishing in one frame. Once that fade elapses the ticker does not restart itself: Park drops _visible, leaves every pen exactly where the fade left it (dark, already-drawn ribbon fully aged out, still allocated — no pool Get/Return), and turns CycleComplete true. RebloomHoldSeconds == 0 is the off switch: never advance the phase at all, draw once and hold, exactly the behaviour before this existed — CycleComplete never turns true either, since Park is only ever reached through this state machine. With the loop off, a multi-host sequence never gets past its first host: nothing ever parks to advance from, so only the sequence's first entry ever draws, and it simply holds — the same "draw once and hold" behaviour a single host gets, just never handed off to the rest of the line.

The controller is what actually decides what draws next, and deliberately so: it is the thing that knows what is sighted, and — since a single prediction line can pass through several item-carrying balloons — what is sighted is now a sequence, not a single host. The ticker never has and still doesn't; it only times one figure's own cycle and reports when it parks. ItemRangePreviewController.LateTick polls ItemPreviewTicker.CycleComplete once per frame, and on a stable, already-shown signature (_shown == true) a true reading calls AdvanceSequence: step _sequenceIndex to the next entry in _sightedHosts, wrapping past the last back to the first, and Show that host's figure — always introduce: true, rather than ShowActiveHost's own introduce rule (which reads "same set as last shown" as a re-settle, not a fresh draw-in — exactly backwards for a cycle that just parked). A single-host line is a one-element sequence, so it advances to itself (0 -> 0 mod 1) every cycle — the sequence collapses to exactly today's single-host loop rather than needing a special case for it. This stays inside the "never re-`Show` a visible figure" invariant precisely because Park already dropped _visible before CycleComplete turns true, mirroring how a real BeginHide always drops _visible before its own re-Show: by the time the controller reacts, the figure genuinely isn't visible any more. Show itself clears _parked (CycleComplete's backing field) as its first act, so the same completed cycle can never be observed twice — whether the controller responds to it or a later Show supersedes it for an unrelated reason. If the controller never responds — the aim left, or the preview is going away entirely — nothing leaks: BeginHide/Hide still release a parked ticker's pens through the ordinary hide path rather than holding them forever, since a parked ticker has nothing left to gracefully fade — its ribbons already aged out — so BeginHide special-cases it straight to a release.

AdvanceSequence updates only the signature's active-host geometry (origin, direction, trace end) to the newly-active host's own values, never _signatureSlots — the sighted set hasn't changed, only the sequence's position within it, and routing the advance through the same full reset StoreSignature uses for a genuine set change would make the very next frame's comparison read the advance itself as a changed aim (HasActiveSignatureChanged would compare the new host's geometry against the old one's stored snapshot and see a "jump"). This is the reason the signature is split into two parts at all: a set half (_signatureSlots, exact per-slot equality, changes only when the aim genuinely moves onto a different group of balloons) and an active-host half (the continuous origin/direction/trace-end of whichever host is currently drawing, changes on every advance and whenever that host itself drifts). Only the set half gates the hide-and-restart in LateTick; the active-host half alone can never trigger it once AdvanceSequence has already brought it into agreement. When the set does change, _sequenceIndex resets to 0 and the newly-settled sequence starts over from its first host, rather than resuming wherever the old sequence happened to leave off — a different group of balloons has no meaningful "where it left off" to resume from. Spin is deliberately absent from both halves — see below.

A spinning host re-blooms instead of resetting, and its turn is bounded so it can't starve the sequence. A Laser's icon (LaserItemRotation) steps between six hex-aligned angles and lerps between them, every single frame, for a quarter of every step — far more often than a settled aim ever drifts. Treating that lerp as part of the active-host signature (as it once was) tore the dwell/settled state down on every one of those frames: BeginHide, _shown = false, the dwell timer restarted, over and over, faster than a full draw/hold/fade cycle could ever complete — so ItemPreviewTicker.CycleComplete never fired and the sequence stuck on the Laser forever. Spin is now tracked entirely apart from the signature (HasActiveSignatureChanged never reads it), and a settled angle change is instead its own re-bloom request: ItemRangePreviewController.HasSpinSettledOnNewAngle compares the raw angle (all the controller ever sees, via IHostsSpinningItem/ISpinningItemVisual) against last frame's reading to tell a lerp still in flight (changing every frame) from one that just arrived and is now dwelling (identical frame to frame, but different from the angle the figure was last drawn at) — no transition-phase signal from LaserItemRotation itself is needed. A settled change calls Show again with introduce: true on the same host, redrawing the figure from scratch at the new orientation without touching _shown, the dwell timer, or the sequence position — the loop stays running, the sequence doesn't move.

Because Show always resets ItemPreviewTicker's own draw/hold/fade clock, every one of those re-blooms restarts the cycle a spin-driven host is otherwise measured against, so a Laser rotating faster than one full cycle would still never let CycleComplete fire on its own — the same problem one level up. _activeHostElapsed, a per-host accumulator that ticks every frame a sequence entry stays active and resets only when the sequence actually advances or the sighted set changes — never by a re-bloom — is what bounds its turn regardless: once it reaches one cycle's worth of time (BloomDuration + RebloomHoldSeconds, the same terms ItemPreviewTicker.AdvanceRebloomCycle already uses for its own draw + hold, rather than a new authored knob), the next settled angle advances the sequence (AdvanceSequence) instead of re-blooming the same host again. This only ever fires at a settled-angle boundary — a dwelling moment, not mid-lerp — so it never interrupts a draw-in the way an advance triggered on an arbitrary frame could. Gated on RebloomHoldSeconds > 0, mirroring AdvanceRebloomCycle's own off switch: with looping authored off, CycleComplete never fires for any host, spinning or not, and this must not either — a Laser with looping off just re-blooms in place on every rotation update, forever, exactly as a non-spinning host's first draw simply holds forever. Non-spinning items are unaffected end to end: their spin reads a constant 0, so HasSpinSettledOnNewAngle never reports a change and they keep advancing purely on CycleComplete, exactly as before.

The loop's fade deliberately authors no second duration: BeginLoopFade reads _fadeDuration off a live pen's trail exactly the way BeginHide already does for a real hide (HighlightTrail. EffectiveRibbonSeconds), and LateTick advances the very same _fadeElapsed/_fading machinery either way. The two only diverge in what happens once that fade elapses, and _cyclePhase is what tells them apart: only BeginLoopFade ever leaves it at Fading, so AdvanceFade parks in that case and releases the pens to the pool in every other case (a genuine BeginHide). A BeginHide arriving while the loop's own fade is already running still wins outright — it redirects that same in-flight fade from a park to a release rather than starting a second one on top of pens already stopped and already ageing, so the preview still disappears for real rather than drawing itself back in. BeginLoopFade itself deliberately never touches _visible: the preview is still showing, just between cycles, so the controller's own signature/dwell bookkeeping keeps reading it as shown for the whole draw/hold/fade arc rather than spuriously treating a mid-loop fade as the aim having left — _visible only drops once the fade actually completes, in Park, the same instant CycleComplete turns true.

The replay covers the approach leg too, not just the figure's own dashes — approach pens have already retired by the time a hold elapses (see AdvanceApproachPen above), so a rebloom that only re-cascaded the figure would leave the comet's tail dead forever after the first cycle. The controller's replay goes through the exact same Show → AcquirePens/AcquireApproachPens path a figure's first appearance does, introduce: true and all, reusing the identical per-pen reset (ResetPenForDrawIn / ResetApproachPenForDrawIn, shared so "what does it mean for this pen to begin cascading in" has exactly one definition instead of a second copy that could drift from the original) — every held pen goes back to Parked/pen-up at the host origin with its ribbon cleared and not emitting, exactly the state AdvancePen's rising edge is built to draw cleanly out of. This is deliberate, not incidental: a settled pen is mid-ping-pong somewhere along its own dash, so jumping it straight back to its dash start while still emitting would draw a straight chord across the whole slot — the exact discontinuous-emit failure the standing rule above exists to prevent, and one this system has produced four different ways already. The parked interval only makes this safer still: every pen has already stopped emitting and sits frozen, dark, the whole time it's held, so there is no window where a pen could be emitting at a position it's about to leave. Held pens are reused rather than re-pooled, though — because a parked pen's Trail is already assigned, AcquirePens'/AcquireApproachPens' pen.Trail ??= … never calls back into the pool for it, so a replay costs no Get/Return churn regardless of whether it draws the same host again or — now that a sequence can advance through several — a completely different one's figure next: the pen itself is just a generic pooled ribbon, indifferent to which item's shape it was last aimed at. The geometry (shape, arc tables, entry offsets, dash counts, cascade timings) is re-derived from scratch on every replay rather than assumed unchanged, since Show no longer has a dedicated restart routine that could skip that work — it goes through one path, acquire or refit, every time, which is exactly what makes drawing a different host's figure next no different from drawing the same one's again as far as the ticker is concerned; only ItemRangePreviewController knows or cares which host's IItemRangePreview and ItemPreviewContext it hands to this Show call. Show resets the loop's phase and clock unconditionally, so a fresh Show (a new host, a fade-in resuming the same one, or a controller-driven advance to the sequence's next host) never starts mid-hold or mid-fade, and can never race an already-due rebloom on the same frame; the clock only advances while the figure is visible and not fading, since AdvanceRebloomCycle runs behind the same LateTick gating that already guards advancing the pens themselves — a hidden, fading, or parked figure never queues up a rebloom that fires the instant it reappears.

Dashing is the one drawing style, not a per-item opt-in. DashLength and DashSpacing are shared across every figure — a Bomb circle dashes at the same size as Shield's stub. Each stroke derives its own dash count from its own length rather than being told a count: with stride = DashLength + DashSpacing, a stroke gets max(1, round(strokeLength / stride)) dashes. A long stroke naturally gets more dashes than a short one, and that count is the pen count for the stroke — one pen draws one dash, and the dashed line is the pens sitting side by side. Ask for a stroke three strides long and you get three pens, each owning a third of it; a two-armed figure with unequal arm lengths legitimately gets a different dash count on each arm, which is the point.

A pen cap bounds the total. MaxPens caps the total summed across a figure's strokes: past it, the stride is inflated once by desiredTotal / MaxPens and every stroke's count is recomputed with the inflated stride. A big figure's dashes come out sparser and longer-spaced rather than any part of it going undrawn. Laser used to be the figure that engaged it: unclipped, its two corridors ran the full RaycastDistance of 20 each way — roughly 160 units of combined perimeter, around 320 pens at the authored stride, well past the cap. Clipping each half-arm to the play area (see the figures table above) keeps both lines under the board's ~9.3-unit diagonal each, so Laser's own dashes no longer reach the cap — the mechanism above still exists for whatever figure does. The approach cascade's own dashes (see the ItemPreviewTicker row's "comet tail" description below) draw from the same MaxPens pool as the figure's — the figure's own dashes derive and claim their count first, and the approach only ever gets whatever remains, inflating its own stride (or, past a fully-spent budget, drawing no approach dashes at all) rather than ever crowding out the payload it leads into.

The gap is pinned; the dash absorbs the rounding, not the other way round. Each stroke's dash count is round(strokeLength / stride), so a stroke's own slotLength = strokeLength / dashCount is almost never exactly stride — rounding a per-stroke length to a whole dash count leaves a remainder, and whichever of {dash, gap} is not pinned has to absorb it. The gap is what the eye reads as rhythm, so it is the one held constant: a pen paints slot − DashSpacing (floored at a small fraction of the slot so a very short stroke, or a spacing authored larger than the stride, still draws something instead of vanishing) and lifts for exactly DashSpacing, on every stroke of every figure regardless of length. That is what lets Laser's two very differently-sized corridors read as the same dash pattern — pin the dash length instead and the gap is what would visibly stretch and shrink between them, since it would be the one left to carry the per-stroke remainder.

Zero spacing reproduces a solid line — there is no separate continuous mode. With DashSpacing = 0, a pen's painted length equals its slot length exactly (slot − 0); adjacent dashes touch with no gap and the stroke reads as one unbroken ribbon. This is why the old DashCount = 0 continuous branch was deleted rather than kept alongside dash mode — the zero-spacing case already produces its output with no separate code path to keep in sync.

A pen sweeps its dash — a → b, then b → a, forever. It never jumps, which is the whole trick: there is no restart to flicker, no discontinuity to hide, and no pen-up at all. The spacing between dashes is simply arc that no pen ever visits, because the painted dash is shorter than the slot its pen owns.

A heavily capped figure trends toward looking solid. Because the gap is pinned rather than the dash, a figure whose dash count the MaxPens cap has reduced gets longer dashes with the same gaps instead of everything scaling up together — the fewer, longer slots each still lose only a fixed DashSpacing to gap, so a heavily capped figure's dashes start to merge visually. This is acceptable today: after Laser's clipping landed (see above), no shipped figure reaches the cap — Laser draws around 37 dashes, Bomb's circle around 22, Paint's triangle around 23, all well under the cap of 64. If a future figure's stroke lengths push it up against MaxPens, this is where to look rather than rediscovering the trade-off from scratch.

A pen goes dark while it is outside the camera's view. ItemPreviewTicker checks every pen's final position each frame against ItemPreviewViewport, the one shared owner of "what is visible" — the camera-derived world rect, refreshed once per frame (not per pen) from Camera.main's orthographic size, aspect, and transform position. This is the general answer to a figure extending past what's on screen when its host sits near an edge: Bomb's circle and Paint's triangle can both do it, and distorting their geometry to fit would misrepresent the effect, so the pen is simply culled for the part nobody can see rather than the shape being bent to stay inside. Culling is a drawing concern, so it measures against what is actually visible — not against the gameplay play-area walls, which the camera frames more than and which don't move, while the camera does (shake, cinematic rigs, the level-transition move); a wall-based box would be both too small and stale. The rect is refreshed every frame rather than cached, precisely because a stale one would cull pens that are still on screen — but the refresh itself is idempotent per frame (ItemPreviewViewport.Refresh guards on Time.frameCount), so both ItemRangePreviewController and ItemPreviewTicker can call it without caring which one runs first. If there is no main camera yet, or it isn't orthographic (the maths above assume orthographic projection), IsActive goes false and culling is skipped entirely — every pen is treated as visible, since drawing something off-screen is a far cheaper failure than a figure silently vanishing. Laser clips its own geometry to this same viewport (see the figures table above), for the pen-budget reason there — an unclipped 40-unit corridor would starve the shared pen budget — falling back to WallLimits only while the viewport itself is unavailable. Crossing back in clears the ribbon before re-enabling it: the trail still holds the points from where the pen left, and re-enabling without clearing would draw a straight chord from the exit point to the re-entry point, which is exactly the jumping trail this cull exists to avoid.

A pen whose slot got reassigned clears its ribbon instead of drawing a chord across the jump. A re-fit (same host, reshaped figure — Laser's hex-stepped rotation is the case that does this constantly) re-derives dash counts and reassigns each pen's stroke/dash slot, which can move a pen's position discontinuously between one frame and the next. ItemPreviewTicker doesn't react to the re-fit itself — that fires on every aim nudge while a host stays sighted, so clearing on it unconditionally would blink the whole figure. Instead it detects the jump per pen: each frame it compares the pen's new position against where it was last frame, and treats anything beyond a small multiple of TraceSpeed × deltaTime (the most a normally-sweeping pen could have covered) as a teleport rather than motion. Only checked once the pen has finished cascading in — mid-cascade a pen can deliberately move far and fast (a waiting pen's jump from its parked spot into its own dash the instant its window opens), which would otherwise trip the same check every frame and suppress the draw-in. Approach pens have no equivalent guard — they're never reassigned to a different dash mid-flight the way a figure pen can be under a refit, so there's no discontinuous jump on them to detect in the first place.

A freshly acquired pen starts pen-up, not pen-down. AcquirePens parks a new or reused pen at the host origin but leaves it not emitting (and clears its stale HasLastPosition baseline, since a reused pen's is left over from its previous figure) — it is AdvancePen's own rising edge, on the pen's first tick, that turns it on, and that edge already clears the ribbon before re-enabling. Seeding a pen emitting at the host origin would draw a straight chord out to wherever it first computed as its real position — a waiting pen's own dash start while it waits its turn, or a settled dash-slot position on a same-host re-settle — the moment it started emitting, since none of those places is the host origin the pen was parked at. Approach pens follow the identical rule at their own scale: AcquireApproachPens parks an introducing one pen-up at the host origin too, and AdvanceApproachPen only ever starts it emitting once it has already been repositioned to its own dash's start. This is a recurring failure mode this system has hit from several angles now (the re-entry, reassigned-slot, approach-versus-cascade, and single-pen-toggling-emitting cases above and below), which makes it worth stating as a standing rule rather than a pile of separate fixes: a pen must never be emitting at a position it is about to leave discontinuously.

"Parked" is wider than just the ribbon: HighlightTrail.SetEmitting toggles the head sprite alongside the TrailRenderer, so a parked pen shows neither a ribbon nor a lone dot sliding around with no ribbon behind it — the head is part of "is this pen drawing," not decoration independent of it. An approaching pen is not parked, so it shows both, exactly as a drawing pen does — the approach is a drawn stroke, not a silent reposition. Every place the ticker starts or stops a pen drawing (AcquirePens parking a fresh pen, the ApplyPenPosition rising/falling edge, BeginHide's graceful stop) already goes through SetEmitting rather than touching the TrailRenderer directly, so this falls out of the existing machinery instead of needing its own case anywhere.

The cull bounds aren't the bare visible rect — ItemPreviewViewport pushes them outward by the stride, IItemPreviewConfig.DashLength + DashSpacing, recomputed alongside the rect each frame. That margin is derived, not authored: the stride is the widest a slot is ever intended to be, and with the gap pinned (see above) a pen's painted dash can run up to a whole slot — so it can exceed DashLength alone once MaxPens inflates the stride on a capped figure. Bounding by the stride is still the smallest expansion that can never clip a dash mid-stroke in every case, including a capped one — a pen even partly on-screen is always drawn in full. It also happens to solve boundary chatter: a pen sweeping its dash near the screen edge crosses a hairline boundary every cycle, and since every re-entry clears the ribbon (the jump above), culling right at the edge would read as a visible stutter instead of the pen simply appearing and disappearing. Shared rather than per-item, since it is about the viewport, which no item owns — and since Laser's own clip reads the same ItemPreviewViewport, cull and clip agree on exactly one notion of "visible" rather than two that could drift apart.

Three wrong turns worth not repeating, all of them attempts to make the gaps by interrupting the pen rather than by bounding where it travels. ClearRibbon cannot make the gaps — clearing wipes every dash already painted, collapsing the figure into one short stroke sliding along it. A pen must not tour the whole stroke leaving dashes behind it: that reads as trails travelling from one end to the other, not as a dashed shape. And a pen must not snap back to its dash start to repeat — each snap ends one ribbon and begins another, so the ribbon lifetime decides how many stale copies pile up, which is what a hard strobe with far too much alpha actually is.

Why a cascade, not a shared travel leg. An earlier version of this scheme had every pen on a stroke travel the same path before drawing — first a straight leg from the host centre, then along the stroke's own arc to the pen's individual dash slot. On a figure with many dashes (Bomb's circle, Paint's triangle) every pen made that same trip at the same time, so N ribbons stacked on top of each other and the shared portion read as one bright, heavy line instead of a figure drawing itself in — Shield only ever looked right because it has a single dash and so nothing to stack against. The cascade replaces that: each pen is confined to its own dash and dashes reveal in sequence — a pen sits hidden at its own dash's start until its turn, sweeps from there to its dash's end, and the moment it finishes the next pen begins, so it reads as one dash drawn after another rather than a shared spoke fading in behind N overlapping copies of itself. The entry point survives this redesign, but its job changes: it no longer defines anywhere a pen travels to, only the order dashes cascade in (smallest forward arc distance from the entry first, via ComputeTravelDistance/AssignCascadeRanks) — every pen still sweeps its own dash in that same forward direction, so the relay reads as one gesture advancing round or along the figure rather than dashes lighting up out of order. What still emerges from the host is the stroke's approach cascade — no longer one pen (CascadeRank == 0) sweeping the whole leg as a single continuous stroke, but its own relay of dedicated ApproachPens, one per approach dash, drawn on the same stride as the figure's own dashes and cascading host-to-entry inside the leg's existing time budget. Unlike a figure dash, each one retires — goes pen-up for good — the instant it finishes, rather than settling into AdvanceDash's ping-pong; a completed figure dash needs to keep looping because it's a permanent part of the shape, but an approach dash is a one-time event on the way to it, and retiring is what turns that one-time draw into a fading comet tail rather than a sequence of held straight lines. A single pen could not draw this fading tail — see the ItemPreviewTicker row above for why toggling one pen's emitting on and off chords across the gaps it tries to leave. See that row for the full mechanics (AdvanceCascade, AdvanceApproachPen, BuildCascadeTimings) and how the standing rule above is satisfied throughout, by both cascades.

Architecture

The item display system is a self-contained, DI-free unit: an ItemDisplayService MonoBehaviour on the host's item container, plus pooled ItemVisualView prefabs (one per ItemType, referenced from ItemSettings.VisualPrefab). The host owns the wiring — it holds a serialized reference to the service and passes every dependency (configs, palette, pool manager) through Bind(), so pooled hosts need no per-instance scope.

Design principle: items are not balloons

The Item/ folder's display side has no dependency on Balloon/. ItemDisplayService.Bind() accepts individual reactive properties — it does not know whether the caller is a balloon, a UI panel, or a reward screen. Future contexts (shop previews, inventory, tutorial highlights) can host items by adding an ItemDisplayService to their hierarchy and calling Bind() with appropriate reactive properties.

IBalloonItem exists only as a thin adapter for the balloon-hosted activation flow. It is the balloon system's way of interacting with items, not the item system's knowledge of balloons.

Display flow

  1. A host (e.g. BalloonView.Bind()) calls ItemDisplayService.Bind(item, colorName, slotIndex, …) with the reactive properties plus the config/palette/pool dependencies and sorting inputs
  2. ItemDisplayService subscribes to the model's Item reactive property and colorName
  3. When the item type changes to non-None, ItemDisplayService gets a ItemVisualView instance from PoolManager.GetOrRegister() keyed by the visual prefab name, reparents it, and calls Activate(color)
  4. When colorName changes while a visual is active, ItemDisplayService calls SetColor() on the active visual — the item display always matches the host's current color
  5. When Unbind() is called or the item changes back to None, the active visual is returned to its pool via PoolManager.Return()
  6. Sorting order updates flow through ItemDisplayService → ItemVisualView.ApplySortingOrder() on the active instance
    • The item icon pool (SimplePoolChannel) does not DI-inject its views, so any visual needing a scoped service is handed it here. Bind() takes an optional SceneLightFieldService; when the spawned visual is a LaserItemRotation, ItemDisplayService calls Configure() on it, passing the light field (so the idle laser can register its telegraph light) and the slot grid's SlotSeparation (so its stepped rotation dwells on hex-aligned angles) — neither can be [Inject]ed
  7. A host that has renderers which must sit above the item passes them nothing directly — instead it reads ItemDisplayService.ActiveItemSortingCount (the item's slot span, 0 when none) and re-layers its own renderers on top. Because the host can't otherwise know when the item's footprint changes, Bind() takes an optional onSortingFootprintChanged callback that fires whenever an item is added/removed; the host re-applies its above-item sorting from there (and on slot moves via its own subscription). BalloonView._aboveItemRenderers is the first user

Activation flow

  1. ProjectileView.OnTriggerEnter2D hands the hit to ProjectileHitResolver, which evaluates the outcome (always Damage = 1) and dispatches an ActorHitMessage through IHitDispatcher (Game/HitPipeline) — score stage first, then the owning BalloonController, then the broadcast
  2. The hit balloon's BalloonController snapshots any ITransformCapture child (publishing TransformCapturedMessage for the laser), calls _view.Hide() (disables collider and renderers), and waits for ItemActivatedMessage before returning to pool
  3. ItemActivator receives the broadcast ActorHitMessage, yields one frame, then calls await Activate(context) (an ItemActivationContext carrying the hit's DamageContext) on the matching handler
  4. The handler runs its effect (may be async, e.g. lightning), dispatching an ActorHitMessage for each secondary balloon with Damage = settings.Damage
  5. ItemActivator publishes ItemActivatedMessage — BalloonController receives it and returns the item balloon to pool

Damage

Each damaging item reads ItemSettings.Damage (configured per item in ItemConfiguration) and passes it inside the DamageContext of the dispatched ActorHitMessage (along with DamageFlags and the source color). The outcome is pre-computed by ActorHitMessage.From, which calls EvaluateHit(context) on the hit actor — BalloonController reads msg.Outcome and routes accordingly. Setting Damage = 1 (the default) reproduces normal one-hit behaviour. Setting it higher on Bomb, for example, allows a single blast to pop tough balloons that would otherwise survive.

Non-damaging items (Paint, Shield, Snipe) do not use the Damage field — the ItemSettingsDrawer hides it for those types.

Unbreakable balloons — UnbreakableBalloonModel returns Deflect from EvaluateHit regardless of damage. Only DamageFlags.Piercing (e.g. the bomb's direct-neighbor blast core) forces a Pop.

Hex-aligned stepped rotation: the laser icon no longer spins freely — it dwells on a hex-grid- aligned angle, then eases to the next one, repeating. HexCoordinates.IndexToWorldPosition places neighbour slots at bearings of roughly 0, A, 2A, 180, 180+A, 180+2A degrees, where A = atan2(SlotSeparation.y, SlotSeparation.x) (≈60° with the shipped separation, so very nearly — but not exactly, since the grid isn't perfectly regular — a hexagon). Because LaserCross fires a four-arm cross, its look repeats every 90°, so only three of those six angles are visually distinct (0, A, 180-A read the same as 180, 180+A, 360-A). LaserItemRotation still cycles through all six in order rather than just those three, spending _stepSeconds on each (the trailing quarter of which eases into the next) — Mathf.LerpAngle always takes the shortest path, and with only three entries the wrap from the last step back to the first would run backwards (~-120°), snapping the cross instead of continuing its turn. Stepping through all six keeps every transition, including the wrap, a forward ~+60°, so the rotation reads as continuous even though its look only has three distinct positions. This is a gameplay change, not just a presentation one: LaserItemHandler captures the icon's rotation at hit time and casts along it, so the beam now always fires along an actual row or diagonal of balloons on the hex grid rather than an arbitrary angle that could slice between them. ISpinningItemVisual.SpinDegreesPerSecond reports 0 for this icon — a stepped rotation has no meaningful constant rate, so the shot solver's gather reads the angle as-is (correct for the dwell, the overwhelming majority of the time) instead of extrapolating along a rate that no longer exists.

Shield chains

Shields placed by the plain weighted draw scatter, and a scattered shield extends nothing — the player picks it up on a flight that was already going to end safely. ShieldChainPlanner instead places them along a flight the thrower can actually fly: each shield is what buys the wall bounce that reaches the next, so shield n makes shield n+1 reachable. ItemAssigner plans the chain once per fill and then hands shields out in flight order.

The narrowing loop (Narrow feeding back into Sweep) is the "a chain is one flight" guarantee — the least obvious thing in ShieldChainPlanner. Each round keeps only the fan angles that still reach every shield placed so far, not just the one just added, so two shields reachable from unrelated angles can never masquerade as a chain.

It plans against a fan of opening angles rather than one, so a chain has several ways in, and keeps only slots reached by enough of the fan — but not by so much of it that the player sweeps them for free. Both bounds, and the fan itself, are authored on RunConfig under ShieldChain (IShieldChainSettings): FanSamples, FanMinDegrees/FanMaxDegrees, MinEntryAngles, CheapZoneFraction. They are balance knobs retuned against playtests, which is why they live on the asset; the planner keeps only the guards that stop it looping (surface epsilon, leg cap).

A chain planned at spawn decays as the board settles, so ShieldReachabilityField re-sweeps a coarser fan on every grid mutation and records the fewest reflections any sampled shot needs to cross each slot. ShieldSlotPreference turns that into a small balance bias — full bonus for a straight-shot slot, less per reflection — which the balancer adds to the actor's own bias rather than obeying, so a shield drifts toward reachable slots without hovering in defiance of the board. ReachabilityFanSamples, ReachabilityMaxReflections, ReachableSlotBonus and PerReflectionPenalty tune it, on the same ShieldChain block.
